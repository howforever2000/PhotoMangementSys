\## 0. 定位与先决判断

\### 0.1 “Python 效率更高”成立的范围

| 操作 | 谁更快 | 依据 |

|---|---|---|

| JPEG 编码（质量阶梯凑体积） | **Python 略优** | Pillow 走 libjpeg-turbo（SIMD）；Rust `image` 同质量通常慢 1.2–1.8× |

| OpenCV 类算法（CLAHE/双边/去噪/超分前后处理） | **Python(cv2) 明显更优** | 真身在 C++ + SIMD/OpenMP，Rust 无等价成熟库 |

| 缩放/裁切 | 基本持平 | Pillow SIMD resampler vs `image::imageops` |

| JPEG 全尺寸解码 | 基本持平 | libjpeg-turbo vs zune-jpeg |

| **DCT 缩略图**（只解 1/2\~1/8 块） | **Rust 更优** | `jpeg-decoder` 的 `scale` 只解所需 DCT 块，比全解再缩快一个量级 |

| 批量文件遍历/EXIF 批量读 | **Rust 更优** | rayon 无 GIL |

| 向量相似度全库扫描 | **Rust 更优** | `vecindex` 连续 f32 + rayon：2.5 万×512 排名 127.8ms → 12.2ms（FEAT-154 实测） |

| Agent 循环本身 | **语言无关** | 99% 时间在等模型 HTTP |

**结论**：图像算法该搬的搬（编码、cv2 类滤镜、合成排版）→ Python；已跑得好的别动（DCT 缩略图、批量扫描、向量扫描、EXIF）→ 继续留 Rust；Agent 循环放 Python 的理由不是“更快”，而是“只留一份实现 + 编排与算法同语言”，代价是必须一次性还清打包账。

\### 0.2 产品形态

用户在一个桌面应用里，通过\*\*下拉选功能（带预置参数）+ 可选自然语言描述\*\*，完成四类图像任务：A 滤镜风格迁移、B 人物美颜、C 主体抽取做成卡片/PDF、D 群照片批量处理及组合。默认路径“点一下就出活”，不花钱、不等待；需要模型理解时才付费。

\## 1. 能力归属表（先立边界再谈代码）

| 能力 | 归属 | 为什么 |

|---|---|---|

| 登录态 / `require_user` / 多用户隔离 | **Rust** | 已有 `SessionState`，Python 不该有第二套身份 |

| Provider 配置 at-rest 加密 | **Rust**（[`crypto.rs`](http://crypto.rs)，AES-256-GCM + `app.key`） | 密钥只在一处落盘加密 |

| 密钥明文 | **仅 Python 进程内存，per-job 注入，用完即弃** | 出网在 Python；token 约束 + 日志脱敏兜底 |

| Agent 编排循环（规划/工具调用/反思） | **Python** | 本次决策 |

| 图像算法（压缩/手账合成/增强前后处理） | **Python** | 本决策 + 编码效率 |

| 规划与执行模型出网（planner + image provider） | **Python**（`httpx`） | 与编排同进程，省一次序列化 |

| 任务注册表（job\_id/cancel/snapshot/事件） | **Rust** | 进程生命周期比 Python 稳；“重启即任务蒸发”不能再来一次 |

| 预算硬闸 / 成本台账落库（`agent_runs`） | **Rust** | 钱与审计要在不会被 kill 的一侧 |

| 上下文装配（意图 → 候选图池） | **Rust** | DB/向量/人物/时间都在 Rust，且这步要确定性可测 |

| DB 读写、文件扫描、缩略图、向量扫描 | **Rust**（不变） | 见 §0.1 |

| OCR / 人脸 / CLIP 编码 | **VCR（Python，已有）** | 不新增，不重复建模型 |

\> **同一个能力在表里只能出现一次。**

\## 2. 三个“不允许”（踩过的坑写成硬规矩）

1\. **不允许两套压缩算法**。压缩要么 Rust 要么 Python，不许两边各一份“凑目标大小”的搜索逻辑——两份必然在“未达标”边界上给出不同结论。过渡期允许两套但必须有对照测试，阶段 3 收口为一份。

2\. **不允许两套密钥路径**。配置只有 Rust 能读写落盘；Python 只接收“本次任务的凭据”，不持久化、不写日志、不进异常栈。

3\. **不允许“没打包的通道”**。任何新增 Python 服务，\*\*先过打包验收再写业务代码\*\*。studio 当年连 `.spec` 都没有，所以从来没进过 `bundle.resources`——用户机器上必然是死的。

\## 4. 进程与生命周期

**不复用 VCR 进程**（两条硬理由）：

\- VCR 启动要加载 ONNX/CLIP（READY 最长 90s，还会触发 GPU 状态机）；Agent 只是 HTTP + Pillow，绑在要预热 90 秒的服务上等于“每次对话先等模型加载”。

\- VCR 的 `ensure_service_ready` 带版本校验，会 `POST /shutdown` 重启服务——任务会随重启蒸发。

**做法：[`sidecar.rs`](http://sidecar.rs) 通用化**，把 [`studio.rs`](http://studio.rs)（`4af7760^` 可取回）里已经踩平的坑参数化：

\`\`\`rust

pub struct SidecarSpec {

    pub name: &amp;'static str,              // "agent"

    pub exe\_in\_resource: &amp;'static str,   // "agent/agent-server.exe"

    pub dev\_entry: &amp;'static str,         // "python/agent\_[server.py](http://server.py)"

    pub instance\_file: &amp;'static str,     // "agent-instance.json"

    pub health\_path: &amp;'static str,       // "/health"

    pub log\_name: &amp;'static str,          // "agent-server.log"

    pub env: Vec&lt;(&amp;'static str, EnvValue)&gt;,

}

\`\`\`

必须原样保留的五条（BUG-2026-0918-009 的血账）：

1\. **实例文件与内存缓存在探活成功后立刻写**，绝不排在“等子进程输出”之后；

2\. **输出读线程绝不 `join`**——服务活着就没有 EOF，join 必然把整个 ensure 卡死；

3\. **kill 必须带 `/T`**（Windows venv 的 `python.exe` 只是启动器，真实解释器是子进程）；

4\. **ensure 单飞**（Mutex + 二次检查）；

5\. **端口每次向 0 要**，写入实例文件；启动失败要\*\*大声失败\*\*并把 stderr 尾巴塞进错误文案。

**启动策略**：懒启动 + 首次预热。进入工坊页时后台 `agent_ensure`（不阻塞 UI）；`agent_submit` 前若未就绪则返回“正在启动（约 1–2 秒）”并自动重试一次。

\## 5. 接口契约（只在 127.0.0.1，只有 4 个端点）

\`\`\`

GET  /health                         → {ok, service:"pm-agent", api:1, planner:bool}

POST /agent/submit                   → {jobId}

GET  /agent/jobs/{id}                → AgentStatus

POST /agent/jobs/{id}/cancel         → {ok}

\`\`\`

请求头统一带 `X-Agent-Token: <AGENT_TOKEN>`（Rust 拉起子进程时通过环境变量注入，Python 侧常量时间比较）；`/health` 免 token（探活用，不记日志）。

`POST /agent/submit` 体（一次把执行所需全部输入给全，\*\*Python 不在执行期回连 Rust\*\*）：

\## 6. 任务、进度与取消

\`\`\`

前端 agent\_submit

   → Rust: require\_user → 扫描互斥 → 开关/预算/provider 校验

   → Rust: assemble（候选池）→ job.begin()（job\_id + cancel flag）→ emit 首个 progress

   → Rust: POST /agent/submit（带 token + 凭据）

   → Rust: spawn 轮询循环（400ms）：

          GET /agent/jobs/{id} → job.merge(status) → emit("agent-progress")

          终态 → ledger 落库（增量成本）→ job.finish\_\* → 停止轮询

   → 前端 store：事件节流渲染 + 700ms 快照兜底（与 scanTask 同构）

取消：前端 agent\_cancel → Rust 置 cancel flag → POST /agent/jobs/{id}/cancel

      轮询循环看到 flag 也直接停（双保险）

\`\`\`

\- **快照真相在 Rust**：`agent_jobs_snapshot` 始终可答（Python 挂了也能告诉用户“中断在步骤 3/5，已花 ¥0.02”）。

\- **Python 崩溃/被 kill**：连续 3 次轮询失败 → `job.finish_err(SidecarDown)`，文案给“重试/看日志”。若最后一次成功快照的 `status` 是 `running`，写入一条 `estimated=1` 的保守成本记录。

\- **成本增量落库**：每次轮询把 `costTotal` 增量写 `agent_runs`（按 step 拆），Python 半路死掉只丢最后 ≤400ms 的量。

\- **单飞 + 扫描互斥**：同一时刻一个 agent job；扫描在跑时拒绝，扫描 `begin` 也检查 agent。

\## 7. 上下文装配（Rust 侧 [`assemble.rs`](http://assemble.rs)）

这是“Python 不碰 DB”的代价，也是最该被测试覆盖的一步（确定性、可复现、无网络）：

1\. 从用户意图粗抽约束：年份/地点/人物/语义词（先用既有 CLIP 文本塔与规则，不调规划模型）；

2\. 各维度召回：`vecindex` 语义 top-K、人物聚类、时间线年份桶、地点桶、\*\*当前 PhotoTray 手选的图\*\*（手选永远优先置顶）；

3\. 去重 + 截断（默认 ≤80 张，硬上限 200），带 `semanticRank` 与元数据；

4\. 附三张“视图摘要”（按年/按地点/按人物计数 + 每组前 3 张路径）；

5\. 产物落 `agent_context` 表（或内存快照）供轨迹回看：“Agent 看到的池子是这 42 张”。

**需要二次检索时**：Python 在 status 里返回 `needReplan: {reason, query, excludePaths}`，Rust 判定后\*\*开一个新 job\*\*（预算与总步数继承），旧 job 标 `handoff`。理由：模型调用不可重放，跨 job 才能让每一步可审计、可复现，也避免“Python 里有个能任意查库的工具”这种越权面。

\## 8. 密钥与出网

\- **落盘**：只有 Rust，`app_settings` KV，值 = `crypto::encrypt(JSON)`；KV key `agent.provider.<uid>.<id>`。

\- **传递**：只在 `POST /agent/submit` 的回环请求体里出现一次；Python 侧用 `SecretStr` 持有，不写日志、不进异常栈、不落盘、不缓存到下一次 job；job 结束后显式置空。

\- **脱敏**：`logutil.redact()` 写任何请求体前先过一遍（Key → `sk-…abcd`；prompt → `<len=312>` + hash）。

\- **默认关**：`agent.enabled=false`。开启时明确告知“会把最多 N 张缩略图发送到你填写的地址”。

\- **Python 进程只监听 127.0.0.1**，`uvicorn` 关 access log。

\## 9. 预算与台账（两层闸）

| 层 | 位置 | 作用 |

|---|---|---|

| 硬闸 | Rust（submit 前） | `maxCost` 与“本次预估”比较；超了直接拒绝，连 Python 都不启 |

| 软闸 | Python（每次模型调用前） | 用注入的 `priceTable` 估本步成本，超限即终止并返回 `status=budget` |

| 记账 | Rust（轮询增量 + 终态补差） | `agent_runs` 行；`cost` 末知时按价格表记估算并标 `estimated=1` |

`priceTable` 由 Rust 用 `include_str!` 内嵌一份 JSON（带 `version` 字段），`agent_price_table` 命令同时喂前端做“预估区间”，\*\*前后端同一份数字\*\*。

**P0/P1a/P1c 的 `maxCalls=0`** 意味着这些路径在代码层面不可能发起模型请求（不是靠自觉，是预算闸拦住）。

\## 10. Skill 三层架构

四个功能按确定性程度分属三层，避免把原子操作包装成宏 Skill，也避免让 Agent 每次从零拼图：

\### 10.1 原子 Skill 层

单步骤、无状态、输入输出明确、需要被多处复用。Agent 可直接调用，Expert Skill 内部也组合它们。

| 原子 Skill | 输入 → 输出 | 成本 | 说明 |

|---|---|---|---|

| `select` | 候选池 + 条件 → 子集 | 0 | 按年份/地点/人物/语义阈值筛，\*\*选图不是修图\*\* |

| `compress` | 图 + 目标 KB/长边 → 图 | 0 | Pillow 质量阶梯 + 缩边 + 居中裁切 |

| `subject_extract` | 图 → 主体 mask/抠图 | 0 或 ¥ | 调分割模型或图像编辑模型 |

| `style_transfer` | 原图 + 参考图 + 指令 → 图 | local=0 / remote=¥ | local 走 LUT，remote 走 provider |

| `beauty_render` | 人像 + 强度档 + mask → 图 | 0 | 检测人脸后仅对人脸区域做磨皮/肤色/亮度 |

| `ocr_extract` | 图 → 文字 | 0（本地） | 调 VCR 的 ocr 通道 |

| `card_render` | 图 + 版式 + 文案 → 单页卡片 | 0 | Pillow 合成，文字由代码画 |

| `pdf_merge` | 多页卡片 → PDF | 0 | 纯确定性 |

\### 10.2 Expert Skill 层

封装一个完整交付物的生产流程，内部展开为一组原子 Skill，负责质检和局部重生成。

| Expert Skill | 内部管线 | 交付物 |

|---|---|---|

| `make_card_set` | subject\_extract → 选版式 → card\_render（每张）→ pdf\_merge | card\_images / card\_pdf |

| `batch_process` | 逐项调用同一原子或 Expert Skill（批量统一风格、批量美颜、批量压缩） | bundle |

| `make_journal` | 分组 → 简报 → journal 排版 → pdf\_merge | card\_pdf |

**Expert Skill 对外只暴露高层语义参数**（图片列表、简报、模板 ID），Agent 不需要知道内部是先分割再排版还是先排版再填充。

\### 10.3 Scenario 层

处理用户需求模糊、涉及多交付物或多路径的情况，决定交付物类型，调度 Expert Skill 或原子 Skill，协调跨交付物的依赖和资产复用。

**不写成一个“群照片处理 Skill”**，因为它的内部路径是不确定的。一旦硬编码，用户下次说“这批照片先统一风格再挑三张做卡片”时又得改 Skill。Scenario 的逻辑放在 [`planner.py`](http://planner.py) 的系统提示和规划循环里——当用户意图涉及“多交付物/多路径”时，规划层先输出一个 `plan` 步骤（分组、路径分配），再逐项调度。

\### 10.4 四功能的归属

| 功能 | 归属 | 理由 |

|---|---|---|

| A 滤镜风格迁移 | 原子 Skill `style_transfer` | 输入输出确定，需被 C/D 复用 |

| B 人物美颜 | 原子 Skill `beauty_render` | 检测→区域约束→编辑封装在内部，会被 D 反复调用 |

| C 主体抽取→卡片/PDF | Expert Skill `make_card_set` | 多步管线 + 确定性排版，需固化版式 |

| D 群照片批量 / 组合 | Scenario 层规划 | 路径不确定，不能硬编码 |

\## 12. 三种提示词分离

这是整套交互能稳的唯一关键。混在一起就会“用户改一个字，排版全变”。

| 名字 | 是什么 | 谁消费 | 用户能改吗 |

|---|---|---|---|

| **RunSpec（执行规格）** | 交付物、范围、模板、强度、引擎、预算——全是枚举/数值，无自由文本 | 执行器（确定性代码） | 通过 UI 控件改，不通过写文字 |

| **PromptTemplate（提示词模板）** | 带槽位的句子骨架：`anchor + {slots} + negative` | Prompt 编译器（确定性渲染） | ❌ 不可改（改了没法复现/批量一致） |

| **TargetPrompt（目标提示词）** | 模板渲染后的最终文本，喂给图像生成模型 | provider（model 类步骤） | 高级区可编辑，但会被校验 + 标记来源 |

**“模型给出目标提示词”精确落成：模型只填 `slots`（受类型与长度约束），最终文本由模板渲染。** 好处：同一预设批量 12 组，锚点段落逐字一致 → 风格一致；换模板只需改数据；出问题能定位到“哪个槽位被填成了什么”。

\## 13. 执行路径 P0–P3 + P1 触发条件矩阵

\### 13.1 路径表

| 路径 | 触发条件 | 是否调 LLM | 目标提示词从哪来 | 成本 |

|---|---|---|---|---|

| **P0 纯预设** | 选了预设，附加描述为空 | 不调 | 模板 + 默认槽位渲染（若消费 prompt）；local 预设直接取 RunSpec | 0 |

| **P1a 规则映射** | 选了 **local 引擎**预设，附加描述非空 | **不调**（本地关键词匹配） | 不产出 prompt；描述映射到 `intensity` 等数值参数 | 0 |

| **P1b 模型填参** | 选了 **remote 引擎**预设，附加描述非空 | 调 1 次（多模态，≤4 图） | 模型产出 `slots` → 模板渲染 | 规划费（千 token 级） |

| **P1c 不消费** | 选了\*\*不消费描述\*\*的预设（`retouch.*`、`card.*`），附加描述非空 | 不调 | 不产出；描述仅存 metadata 供轨迹回看 | 0 |

| **P2 完全自定义** | 选“完全自定义” | 调 1 次（判定 + 填参，必要时澄清） | 同 P1b | 规划费 + 可能的澄清一轮 |

| **P3 手改目标提示词** | 用户在高级区直接编辑 TargetPrompt | 不调 | 用户文本（+ 强制锚点） | 0 规划费 |

**P0 是默认路径，也是最重要的一条**：绝大多数使用不该触发模型规划，产品“点一下就出活”靠这条。

\### 13.2 P1a 规则映射表

`engine: local` 的预设的附加描述走纯本地规则，\*\*不触发任何出网请求\*\*：

| 用户描述关键词 | 映射到 | 示例 |

|---|---|---|

| 暖、更暖、温暖、夕阳、黄昏 | `intensity` +1 档 | “再暖一点” → moderate → strong |

| 冷、更冷、清冷、清爽 | `intensity` -1 档 | “淡一点” → moderate → subtle |

| 强、重、浓、猛 | `intensity` = strong | “浓一点” → strong |

| 弱、轻、淡、自然、轻一点 | `intensity` = subtle | “自然点” → subtle |

| 未命中任何关键词 | 不修改参数，UI 内联提示：“当前预设仅支持调整强度（更暖/更冷/更强/更弱），未识别到相关描述。如需 AI 重绘请切换至 AI 插画化或使用完全自定义。” | — |

命中后 `CompileOutput.prompt_source = "rule_mapped"`，`prompt = None`，`assumptions` 记一条。\*\*不做 local 预设的模型调用兜底\*\*：local 路径的核心卖点是零成本零延迟，用户写“像莫奈那样”不是 local 预设该处理的，应引导切 remote。

\### 14.2 PlanPatch 白名单

\`\`\`json

{

  "deliverable": "card\_pdf",

  "scope": { "mode": "tray" },

  "style": { "preset": "warm\_dusk", "intensity": 0.6, "engine": "local|remote" },

  "retouch": { "faces": true, "strength": "natural|mild" },

}

\`\`\`

**不在白名单里的一律丢弃**（模型输出 `"steps": [...]` 想自己排管线 → 直接扔掉，不执行）。\*\*scope 在 P1 冻结为 tray\*\*，P1 的 patch 若带不同 scope 直接丢弃并记 assumption；P2 改 scope 走 §17.3 的 needReplan。

\### 14.3 渲染（确定性）

\`\`\`python

def render(tpl: PromptTemplate, slots: dict) -&gt; str:

    body = tpl.skeleton.format(\*\*{k: v for k, v in slots.items()})

    return f"{tpl.anchor}\\n\\n{body}".strip()   # anchor 永远在最前，且不可省略

\`\`\`

三条硬规则：

1\. **anchor 必须原样出现在最终文本开头**（防模型改写过度丢掉构图约束）；

2\. **negative 只来自模板**，模型不许补（模型补的负面词常和正面词打架）；

3\. 渲染后文本 `len` 超模板 `maxChars` → 依次截断 `note` → 降 `intensity` 一档（记 assumptions）。

\### 14.4 多模态额度合并计数

| 用途 | 张数 | 长边 | 何时传 |

|---|---|---|---|

| 判断交付物/分组/主体 | **≤4（含参考图）** | 512 | P1b / P2 |

| 判断风格参考（“像这张”） | 1（占上方 4 张中的 1 个名额） | 768 | 有参考图时 |

| 判断主体是什么（卡片标题用） | ≤4（同上） | 512 | C/D 且用户没给标题 |

**合并规则**：一次多模态请求总图数 ≤4。tray 4 张 + 1 参考图 → thumbs 截断到 3，参考图占第 4 个名额。\*\*规划阶段绝不传原图\*\*（用 `preview::ensure_into(dir, path, 512)`，Rust 侧已有缓存）。

\## 16. 校验与冲突

\### 16.1 校验（任何 P1/P2/P3 输出都要过）

| 校验 | 规则 | 失败处理 |

|---|---|---|

| schema | 白名单字段 + 枚举 + 数值范围 | 回灌错误原文，自修 1 次；仍失败 → 丢弃 patch，按 P0 执行并记 assumption |

| 槽位 | enum 必须在 values 内；text ≤ maxLen | 截断 + 记 assumption |

| 锚点 | 最终 prompt 必须含模板 anchor 首句（P3 也要求前置） | 自动补回 anchor 到开头 |

| 禁用词 | `watermark, logo, 签名, 微信号, 二维码, 联系方式` | 命中即剔除并记 assumption |

| 隐私 | **不允许**把人物真名写进 prompt（人名只用于分组/挑图） | 替换为 `the person`，记 assumption |

| 覆盖冲突 | 预设 card\_pdf，用户说“不要 PDF” | 改 deliverable，记 conflicts，UI 顶部提示“已按你说的不出 PDF” |

| 编造路径 | patch 里的图片路径必须属于 candidates/tray | 丢弃该路径 |

| scope 变更 | P1 带非 tray scope | 丢弃 scope 字段，记 assumption |

\### 16.2 冲突表（首批，可回归测试）

| 预设 | 用户说 | 结果 |

|---|---|---|

| card\_pdf | “不要 PDF” / “发朋友圈” | → card\_images |

| card\_images | “打印” / “给我一份文件” | → card\_pdf |

| style.local | “AI 画一下” / “插画” | → engine=remote（未配 provider 则提示） |

| retouch.natural | “再自然一点” | → strength=mild（不是强度 0） |

| 任意 | “别改人脸” | → retouch.faces=false |

| batch | “先给我看一张” | → sample\_first=true（默认就是） |

\### 16.3 scope 变更矩阵

| 路径 | 允许改 scope？ | 变更后的落地方式 |

|---|---|---|

| P0 | 否（无模型参与） | — |

| P1a / P1b / P1c | **否** | patch 里 scope 被丢弃，记 assumption“P1 不允许扩大范围，已按当前托盘执行” |

| P2 | **是** | Python 返回 `needReplan: {reason: "scope_changed", query: "2023@杭州"}`，Rust 关旧 job、开新 job（预算与总步数继承，旧 job 标 handoff） |

| P3 | 否 | 手改提示词不改变处理范围 |

**P2 的 needReplan 流程**：Python 返回 needReplan → Rust 检查预算（新范围可能意味着更多图 × 每张成本）→ 预算够则 assemble 重装配 + 开新 job；不够则 `finish_err(BudgetExceededForRescope)`，前端提示“扩大到 24 张预计花费 ¥3.6，超过当前预算 ¥0.5”。UI 上必须有确认弹窗：“Agent 想处理 2023 年在杭州拍的全部 24 张图，是否继续？”——\*\*不能静默扩大\*\*。

**为什么 P1 禁止改 scope**：P1 定位是快速执行不打断用户。用户选 8 张点开始，Agent 悄悄扩到 24 张、账单从 ¥0.15 变 ¥0.45，是 BYOK 最忌讳的行为。

\### 16.4 P3 超长与批量

**超长**：UI 内联红字“已超出 N 字，超出部分将被忽略（上限 800）”；提交时后端按 maxChars 硬截断，记 assumption；截断后仍做锚点校验，若把 anchor 切掉则自动补回。

**批量**：P3 用于批量时直接拒绝，UI 提示“手改提示词模式仅支持单图处理。批量任务需要为每张图独立填充槽位，手改会导致所有图使用同一份描述。请使用预设或 P1b/P2。” 若用户需要“批量但统一提示词”，应使用 `card.*` 预设的 `layout.title` 字段填统一文案（RunSpec 范畴，不是 TargetPrompt）。

\## 17. UI 细节

1\. **下拉里只放能跑的**：`planned` 灰掉标“规划中”；`needs_key` 标“需配置模型服务”并给跳转。

2\. **按钮文案随状态变**：`开始（按预设）` / `开始（按你的描述）` / `开始（已套用你的提示词）`。用户一眼知道这次有没有花钱让模型理解。

3\. **高级区默认折叠**，展开后两行：`目标提示词`（可编辑等宽，标模板版本或“你编辑的”）+ `这次会做什么`（人话列表：抠主体 × 8 → 排版 magazine\_3up → 导出 PDF 3 页 → 预估 ¥0.00）。

4\. **按预设执行时高级区展示随引擎类型变化**：

   \- **remote 引擎**：显示渲染出的目标提示词（只读灰），可编辑转 P3。

   \- **local 引擎**：\*\*不显示提示词\*\*，显示“执行参数预览”：`本地滤镜 · 色温 +8 · 高光 -15 · 饱和度 +6 · 强度 moderate`，下方小字“本预设使用本地算法，不涉及模型提示词。如需 AI 重绘请切换至 AI 插画化或使用完全自定义。”

   \- **不消费 prompt 的预设**（retouch/card）：显示执行参数预览（美颜强度档/卡片版式名/页数）。

5\. **P1b 完成后**：轨迹第一条显示“你的描述被转成：{渲染后的 prompt}” + 可点开的差异（槽位 before/after）。

6\. **P1a 完成后**：轨迹显示“描述‘再暖一点’已映射为 intensity=strong（本地规则，零成本）”。

7\. **重试**：整单重试 = 同 recipe 同 slots 换 seed；只改一个槽位要能在轨迹里点（“强度→strong”），这是局部重生成在 UI 上的对应物。

\## 18. 成本模型

| 路径 | 规划成本 | 执行成本 |

|---|---|---|

| P0 | 0 | local=0 / remote=按张 |

| P1a（local 规则映射） | **0** | local=0 |

| P1b（remote 填参） | 1 次多模态调用（≤4 图 × 512px + 短文本 ≈ 数百 token 图） | remote 按张 |

| P1c（不消费描述） | **0** | 按预设执行 |

| P2（完全自定义） | 1 次多模态调用（同 P1b）+ 可能的澄清一轮 | 按执行路径 |

| P3 | 0 | 同上（用户提示词可能更长 → 输出侧 token 略增） |

**边界写死**：`budget.maxCalls` 里把“规划调用”计为 1 次。P0/P1a/P1c 的 `maxCalls=0` 意味着这些路径在代码层面不可能发起模型请求。

class OpenAICompatProvider(ImageProvider):

    async def edit(self, req: EditRequest) -&gt; EditResult:

        headers = {"Authorization": f"Bearer {self.api\_key}"}

        if self.async\_poll:

            # Seedream：提交 → 轮询

            async with httpx.AsyncClient(timeout=30) as client:

                submit = await [client.post](http://client.post)(f"{self.base\_url}/images/generations",

                    headers=headers, json={"model": self.model, "prompt": req.prompt,

                    "size": req.size or "1024x1024", "n": 1})

                task\_id = submit.json()["task\_id"]

                for \_ in range(60):

                    await asyncio.sleep(3)

                    poll = await client.get(f"{self.base\_url}/tasks/{task\_id}", headers=headers)

                    data = poll.json()

                    if data["status"] == "completed":

                        img = await client.get(data["result"]["url"])

                        return EditResult(image\_bytes=img.content, cost=data.get("cost"), model=self.model)

                raise TimeoutError(f"seedream task {task\_id} not completed")

        else:

            # 同步 OpenAI 兼容图像编辑

\### 19.2 Agent 编排循环（手写，约 250 行）

\`\`\`python

\# agent/[runtime.py](http://runtime.py)

MAX\_STEPS = 5

MAX\_REFLECTION\_RETRIES = 1

async def run\_agent(user\_msg, image\_paths, planner\_client, planner\_model, image\_provider, recipe, p1\_path):

    messages = [{"role": "system", "content": SYSTEM\_PROMPT},

                {"role": "user", "content": build\_user\_content(user\_msg, image\_paths)}]

    reflections = 0

    for step in range(MAX\_STEPS):

        resp = await planner\_[client.chat](http://client.chat).completions.create(

            model=planner\_model, messages=messages, tools=TOOL\_SCHEMAS, tool\_choice="auto")

        msg = resp.choices[0].message

        if not msg.tool\_calls:

            return {"text": msg.content, "status": "done"}

        for call in msg.tool\_calls:

            args = json.loads(call.function.arguments)

            result = await dispatch([call.function.name](http://call.function.name), args, image\_provider, recipe)

            messages.append({"role": "tool", "tool\_call\_id": [call.id](http://call.id),

                             "content": json.dumps(result, default=str)})

            if result.get("image\_bytes") and reflections &lt; MAX\_REFLECTION\_RETRIES:

                verdict = await reflect(result, user\_msg, planner\_client, planner\_model)

                if not verdict["ok"]:

                    reflections += 1

                    messages.append({"role": "user",

                        "content": f"上一次结果不满足：{verdict['reason']}。请修正。"})

    return {"text": "任务达到最大步数", "status": "max\_steps"}

\## 21. 常见坑

| 坑 | 表现 | 处置 |

|---|---|---|

| 把模板当提示词给模型改 | 用户改一个字，风格全变、批量不一致 | 模板只读；模型只填槽位 |

| 预设“没有提示词”的错觉 | 用户以为写描述能改排版 | 消费矩阵进 UI；“这次会做什么”始终可见 |

| P0 也被加上 LLM | 点一下等 2–3 秒还花钱 | `maxCalls=0` 硬闸 + 出网计数测试 |

| local 预设写描述白花钱 | 用户花了规划费等 3 秒，描述完全没影响结果 | P1a 规则映射，不调模型 |

| 模型悄悄扩大 scope | 账单从 ¥0.15 变 ¥0.45 | P1 冻结 scope，P2 走 needReplan + 确认弹窗 |

| 目标提示词太长 | 远程模型报错/效果漂 | 模板 `maxChars` + 渲染后截断策略 |

| 模型在 prompt 里写中文文案 | 生成图里出现乱码字 | anchor 固定 `no added text`；文案由代码画 |

| 槽位枚举被模型“创造性”扩展 | 出现 `warm_dusk_v2` 不存在的预设 | 枚举校验 + 非法值回落默认并记 assumption |

| 参考图被当成“要换脸” | 生成图换了人 | anchor 固定 `preserve faces and identity`；`faces_intact` QA 兜底 |

| 配方 id 与既有 preset 撞名 | 前端两套 preset 混用 | 代码统一 `recipe.*` 命名空间 |

| Pillow 中文路径静默失败 | 写出 0 字节文件 | [`compress.py`](http://compress.py) 用 `open(fileobj, "wb")` 传文件对象给 Pillow，不传路径字符串 |

| 打包又漏了 | 用户机器上“Agent 一直启动中” | 阶段 0 冒烟脚本进 CI；`release.ps1` 产物自检（需 7-Zip） |

| sidecar 起不来 | `/health` 不通 | 错误文案给 stderr 尾巴 + “重试/看日志” |

| Python 挂了任务卡死 | 轮询连续失败 | 3 次失败 → `finish_err(SidecarDown)`；实例文件保留收养 |

| 密钥进日志 | 日志出现 `sk-` | `redact()` + 单测断言；CI grep |

| 压缩两套实现漂移 | 同图两边结果差 &gt;5% | 对照测试；阶段 3 统一实现 |

| 风险 | 触发表现 | 兜底 |

**整体回退**：`agent.enabled=false` 时，工坊退化为 v0.4.5 的工具台（压缩走 Rust、无 Agent），不残留任何依赖——这条作为硬约束写进代码（`agent` 模块不得被 [`tools.rs`](http://tools.rs) / 扫描链路反向依赖）。

**什么时候该回退 v1（Rust 编排）**：如果阶段 0 之后仍反复出现“用户机器上 sidecar 起不来”（且不是可修的文案问题），说明这笔进程税在这个用户群上收不回来——那时把 Agent 循环搬回 Rust（`agent/`[`run.rs`](http://run.rs)），图像算法留在 Python（VCR 或后续端点），是唯一合理的中转。

\## 25. 需要拍板的事项

1\. **压缩实现**：过渡期接受“两套 + 对照测试”（建议），还是阶段 1 就直接把 `image_compress` 迁到 Python（前端零改动，但工坊从此依赖 sidecar）？

2\. **窗口依赖**：确认“Agent 任务必须在应用窗口打开时跑”（本方案默认如此，因为取消与轨迹都走前端事件；若要后台常驻跑需额外设计托盘/通知）。

3\. **`agent-server.exe` 体积预算**：Pillow-only（≤40MB，推荐）还是允许带 opencv（+40MB，换来本地滤镜类算法）？

4\. **P1 是否允许改交付物**：建议“只有明确冲突才允许”（如“不要 PDF”），其余只许填参——否则用户选了下拉又被模型改掉会困惑。是否更宽松？

5\. **高级区默认是否展示目标提示词**：建议首次使用时展示一次，之后折叠。

6\. **首批配方数量**：建议 4 个（风格 1 + 美颜 1 + 卡片 1 + 批量 1）先验证交互，不做 8 个。

7\. **模板语言**：建议\*\*模板存英文、锚点英文、槽位值中英双写\*\*（`look.warm_dusk` 渲染成 `warm dusk (warm_dusk)`），换模型不用改模板。
