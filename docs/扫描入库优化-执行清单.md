## 二、问题全景（为什么需要这张清单）

### 2.1 当前「增量」只覆盖 7 条腿里的 2 条

| 分支 | 现在增量会跳过吗 | 单张成本 | 已入库相册的实际开销 |
|---|---|---|---|
| 目录遍历 | ❌ 全走 | 磁盘 IO | 走一遍（语义分支还走第二遍） |
| EXIF 读取 | ❌ 全读 | 打开+解析 | 读一遍（勾 AI 时读两遍） |
| **影调分析** | ❌ **全解码** | **完整图像解码（最贵）** | **逐张解码** |
| 图像向量 | ✅ 跳过 | HTTP+推理 | 0 |
| AI 识别 | ✅ 跳过 | HTTP+推理 | 0 |
| 描述索引 | ❌ 全量重算 | 读全表+算指纹 | 全表扫一遍 |
| 缩略图预热 | ❌ 全册 | 解码+缩放 | 全册 |

**根因**：判据只挂在 AI 与图像向量两条腿上；而影调/EXIF **在非 AI 扫描时根本不落库**，没有「做过」的证据可查，所以无法跳过。

### 2.2 四阶段严格串行 = 「后台资源没占满」

| 阶段 | 性质 | 期间微服务 | 期间 CPU |
|---|---|---|---|
| walk（同步在 async 上下文） | 磁盘 | 空闲 | 空闲 |
| EXIF（N 线程，实测峰值 2） | IO 等待 | **空闲** | 大量空闲 |
| 影调（**单线程**） | 纯 CPU | **空闲** | 只 1 核 |
| 图像向量 → AI（串行 HTTP） | 等微服务 | 忙 | 空闲 |
| build+upsert | 同步 | 空闲 | 1 核 |

### 2.3 第一性原理约束（不可违反）

- `python/vcr/model_registry.py:115`：`intra_op_num_threads = 逻辑核数`、`inter_op_num_threads = 1`。
  ⇒ **微服务是 CPU 饱和瓶颈，客户端并发请求 = 核心超订，不是加速。**
  ⇒ 对微服务的访问**必须串行化**；图像向量与 AI 两个 HTTP 阶段**绝不互相并行**。
- `content.rs:325` `photo_hash(path, len, mtime)`：只算 `stat` 三元组，**不读文件内容**。
  ⇒ 微秒级 vs 解码毫秒级，**差三个数量级**，是唯一合理的增量判据。
- EXIF 是 IO 密集、微服务是 CPU 密集，二者**资源正交** ⇒ 唯一安全的阶段重叠。

## 三、逐项施工说明

### P1 · 收尾需求位丢失竞态

**解决什么问题**
连扫多个相册时，后一个相册登记的「描述索引 / 分类重建」需求可能被前一个正在跑的收尾任务忽略 → 索引静默不更新 → 刚扫的照片用时间/地点搜不到。

**代码层面改动方案**
`src-tauri/src/content.rs:1660-1670` 把「检查需求位」从释放锁**之前**移到**之后**，并加 CAS 重入：

```rust
// 旧（有洞）：先查需求 → 再释放。窗口内生产端登记的需求丢失。
let again = post_round_should_continue(round, MAX, desc.load(), rebuild.load());
if !again { break; }

// 新：先释放 → 再复查 → CAS 抢回
running.store(false, Ordering::SeqCst);
if desc.load(SeqCst) || rebuild.load(SeqCst) {
    if running.compare_exchange(false, true, SeqCst, SeqCst).is_ok() {
        continue;          // 抢回，再跑一轮
    }
    // CAS 失败 = 别人已接手，安全退出
}
break;
```

**原因**
生产端（`content.rs:1549` 先 `swap(true)` 再 `store(true)` 需求位）在消费端持锁期间登记需求；消费端若在释放前查完就退出，这条需求永远没人认领（经典 lost-update）。必须「先释放、再复查、CAS 抢回」，用 `SeqCst` 保证跨线程顺序。

**验证**：单测构造「consumer 查完 + producer 登记 + consumer 释放」的交错序列，断言需求位最终被消费。

### P2 · 影调/EXIF 结果落库

**解决什么问题**
（1）只勾「影调 / EXIF」扫描时结果**不写库**，刷新页面即丢；（2）这是增量扫描做不了的总根源——没有「这张做过」的记录，就无法判断能否跳过。

**代码层面改动方案**

```rust
// 非 AI 分支：构建 all_rows 之后
```

### P3 · 收尾完成事件漏通知被合并相册

**解决什么问题**
B 相册的收尾请求被合并进 A 的任务后，任务结束只发 `album_id: A`，B 的「索引更新中」徽标**永久不消失**。

**代码层面改动方案**
`content.rs:1674-1686` + `src/stores/content.ts:491`。给 `PostScanState` 加被服务相册集合：

```rust
pub struct PostScanState {
    pub running: AtomicBool,
    pub rebuild_needed: AtomicBool,
    pub desc_needed: AtomicBool,
    pub served_albums: Mutex<HashSet<i64>>,   // 新增
}
```
生产端合并时 `served_albums.insert(album_id)`；任务结束逐个 emit，或统一发 `album_id: null` 触发前端全清（前端 else 分支已支持）。

**原因**
单飞锁是进程级的，一个任务可能服务多个相册；事件必须覆盖所有被服务的相册，否则 UI 状态机不闭合。

**验证**：连扫 2 个相册（第二个落在收尾窗口内）→ 两个相册的徽标都应恢复。

### P6 · 后台收尾与新扫描争抢微服务

**解决什么问题**
T3 把收尾转后台后，用户可以立刻发起下一次扫描，而 A 的收尾（描述索引 / 分类重建）正在调 CLIP 文本塔。两者打同一个单实例微服务（`intra_op=核数`、`inter_op=1`）→ 核心超订、互相拖慢。

**代码层面改动方案**
`content.rs:1604` 的收尾循环每轮开始前让路：

```rust
// PostScanState 加 foreground_busy: AtomicBool
// 扫描命令进入置 true、退出置 false
for round in 1..=3 {
    while post.foreground_busy.load(SeqCst) {
        tokio::time::sleep(Duration::from_millis(200)).await;
        if crate::scan_cancelled(&scan) { break; }
    }
    ...
}
```

**原因**
微服务是 CPU 饱和瓶颈（`intra_op` 吃满核、`inter_op` 串行），并发请求 = 核心超订，不是加速。客户端必须串行化对它的访问。**这是 T3（收尾后台化）引入的新副作用，原始 v3 清单里没有。**

**验证**：先扫 A（触发收尾）→ 立即扫 B → 观察 `[vcr.stat]` / `[scan.batch]` 日志，B 的批耗时不应因 A 的收尾显著上升。

### P8 · 增量统一判据：photo_hash 差集

**解决什么问题**
现在每条腿各自为政，有的跳过有的不跳，判据也不统一（AI 用 album 内哈希集合、向量用全局哈希+档位、影调/EXIF 无判据）。

**代码层面改动方案**
`scan_album_combined` walk 之后新增一步：

```rust
// 1. 逐张算 hash（复用 content.rs:325 photo_hash）
let ingested: HashSet<String> = db.lookup_scanned_hashes_by_album(album_id)?;
let pending: Vec<PathBuf> = all_paths.iter().filter(|p| {
    let (len, mtime) = stat(p);
    !ingested.contains(&photo_hash(p, len, mtime))
}).cloned().collect();
logger::log_info(&format!(
    "[scan.incr] album={album_id} 差集 | 目录 {} 张 · 待处理 {} 张 · 已入库未变 {} 张",
    all_paths.len(), pending.len(), all_paths.len() - pending.len()
));
```

**原因**
`photo_hash` 只算 `(len, mtime, path)`，是微秒级 `stat`；解码是毫秒级，**差三个数量级**。统一判据可避免「某条腿漏判 / 误判」，也让四条腿的跳过数在 `[scan.summary]` 里能自洽对账。

**注意**：判据含 `mtime` ⇒ 用户手动改图会视为新照片重算，**这符合预期**。

### P10 · 相册级「零变化」早退

**解决什么问题**
全局批量增量扫多个已入库相册时，每个仍要走完全部阶段。

**代码层面改动方案**
差集为空 → 直接返回：


### P11 · 收尾任务 panic 守卫

**解决什么问题**
收尾任务若 panic（detached 任务），`running` 停在 `true`，本会话所有后续收尾被永久挡掉且**无任何日志**。

**代码层面改动方案**
`content.rs:1604` `run_post_scan_tasks` 开头建 RAII guard：

```rust
struct RunningGuard(tauri::AppHandle);
impl Drop for RunningGuard {
    fn drop(&mut self) {
        self.0.state::<crate::PostScanState>()
             .running.store(false, Ordering::SeqCst);
    }
}
let _guard = RunningGuard(app.clone());
```

**原因**
`tauri::async_runtime::spawn` 的 detached 任务 panic 后不会有人接管，`running` 永久为 `true`；RAII 保证锁一定释放，是并发编程的基本防御。

**验证**：注入一次 panic，断言 `running` 复位、下一次扫描收尾仍能启动。

### P12 · 影调分析并行化

**解决什么问题**
`tone.rs:58 analyze_paths` 是 `paths.iter().map(...)` **单线程**（全仓无 thread/spawn/rayon），多核机器上只用一个核，而影调恰是最贵的本地分支。

**代码层面改动方案**

**原因**

**⚠ 前提**：若先做了 P13 阶段重叠，影调会与微服务争核，**需重测后决定是否保留并行**。执行顺序上 P12 应在 P13 之前，或在 P13 落地后重新评估。

**验证**：`[scan.phase] tone=` 耗时应显著下降；`cargo test --lib` 中 `analyze_paths_parallel` 与 `analyze_paths` 结果逐字段一致。

### P13 · EXIF 与 HTTP 阶段重叠

**解决什么问题**
四阶段严格串行 → EXIF/影调跑时微服务空闲、HTTP 等回包时 CPU 空闲——**这就是「后台资源没占满」的结构性原因**。

**代码层面改动方案**
`content.rs:1214-1430` 用 `futures::join!` 并发：

```rust
let (exif_res, sem_res) = futures::join!(
    tauri::async_runtime::spawn_blocking(move || read_exif_paths_parallel(&p, t)),
    scan_album_embeddings(...),

```
- **只重叠 EXIF（IO 密集）与 HTTP 阶段（CPU 密集）**；
- 影调（CPU 密集）是否并入需实测（与微服务争核）；
- **绝不重叠两个 HTTP 阶段**（见 2.3 的核心超订约束）。

**原因**
EXIF 用磁盘带宽、微服务用 CPU，二者资源正交，重叠是纯收益。

**前置**：必须先完成 P6 的「微服务访问串行化」，否则重叠会加剧争抢。

**验证**：`[scan.phase]` 汇总里 `exif` 与 `semantic` 时间出现重叠；总耗时下降且批耗时不上升。

### P14 · DB 单连接 Mutex → 只读连接池

**解决什么问题**
`db/mod.rs:209` 开了 WAL（注释称「写不阻塞读，读不阻塞写，并发性能 10~50×」），但 `AppState(Mutex<Database>)` 只有一个 `Connection`，所有访问被 Rust 侧 Mutex 串行。`load_desc_sources`（`db/content.rs:844`，读**全部**照片行）持锁期间，UI 的任何读表都被卡——**这是「后台收尾卡 UI」的结构性根因**。

**代码层面改动方案**

**原因**
WAL 的并发读能力被 Rust 侧单连接 Mutex 完全抵消。这是较大重构，可后置，但收益是全局 UI 流畅度。

### P19 · 语义腿缩略图生成并行化 + 进度埋点 ✅ 已完成

**解决什么问题**
语义腿 `scan_album_embeddings` 内部生成缺失缩略图时，写的是 `missing.iter().filter_map(...)` **单线程串行**且**零埋点**。实测日志（album=63，412 张）：

- 它是三腿并发里的**关键路径** —— AI 腿 41.6s 就跑完，随后**空等 154s**；
- 期间日志完全空白（22:57:08 → 22:59:17 共 129 秒零输出），用户看到进度 100% 却卡着，无法归因。

**代码层面改动方案**

1. `src-tauri/src/thumbnail.rs` 新增 `ensure_grid_thumbs_missing_parallel(album_id, missing, thumbs_dir, user_id, on_progress)`：按 `available_parallelism().min(8)` 分块 `std::thread::scope` 并行，**按下标落位保证输出顺序与输入一致**，样本 < 2×线程数时退化串行；`on_progress(done, total)` 每张回调一次。
2. `src-tauri/src/content.rs` 语义腿第 2 步改调它，并加三档日志：

3. 顺手用 `std::mem::take(&mut missing)` 替代原来的 `missing.clone()`，省一次 412 项克隆。

**原因**

- **缩略图生成是 embarrassingly parallel**：每张独立解码 + 缩放 + 编码，无共享瓶颈、无共享状态，与影调分析（P12）同性质 —— P12 已并行，而这里漏了。

**实测数据（release，96 张真实照片，先预热页缓存再计时）**

```text

```

4. 新增**源码级回归测试** `desc_index_rebuild_called_on_both_scan_paths`：断言函数定义 1 次、调用 2 次、且至少一处排在最后的 upsert 之后。真跑需要 `AppHandle` + 识别服务，而该缺陷的**实际失败模式就是「调用点被删」** —— 源码断言正好锁住它。

**原因**

- **硬约束**：描述分段的年份来自 `shoot_time`、地点来自 `location`，二者由该 upsert 写入；若在落库前编码，`source_hash`（基于描述分段算）会把「缺年份地点」的错误指纹**固化，之后永不重算** —— 比不建索引更糟。
- **为什么必须覆盖早退路径**：缺口照片的 `photo_hash` 已在库内 → 差集必空 → 早退 → 不覆盖则 album 57/36 重扫永远补不回。
- **为什么全库而非仅本相册**（与原清单 Q6 不同，已单独提异议并被采纳）：全库复用现成函数、零签名改动，且更彻底（顺手补掉任何历史缺口）；相册级过滤要动 `db::load_desc_sources`，属 P14（DB 连接/锁优化）的范畴，P0 不扩大改动面。

**成本（实测本机库）**

| 阶段 | 量 | 说明 |
|---|---|---|
| 读全表 | 14621 行 | ≈10~30ms 持锁 |
| 指纹短路 | 5801 条跳过 | `source_hash`，零成本 |
| 待编码照片 | 8820 张 | → |
| **去重后送文本塔** | **≈3130 种唯一描述**（去重率 **78.6%**） | 文本按去重后编码 |

→ 首次补建**几秒到十几秒，且只发生一次**；之后 pending 为空、整体几十毫秒。

### P20 · 模型体积三口径统一标注 ✅ 已完成（本轮）

**解决什么问题**：用户看到「档位 754MB / 会话实测 345MB」，判断为「加载的模型和会话实测不一致」。

**真相（实测核算，推翻了我初判的「bytes 与磁盘对不上」）**：

| 口径 | 字节 | MiB | 十进制 MB |
|---|---|---|---|
| 图塔 `clip_vision.onnx` | 345,193,788 | 329.2 | **345.2** ← 会话实测报这个 |
| 文本塔 `clip_text.onnx` | 408,709,491 | 389.8 | 408.7 |
| 双塔合计 | 753,903,279 | **719.0** ← label 原先写死的 | 753.9 |
| `meta.bytes` | 753,665,706 | 718.8 | **753.7** ← UI 显示的 |

**所以719 与 754 是同一个文件的两种单位**（MiB vs 十进制 MB），数值本身没错；真正的矛盾有两条：① **单位不统一**（label 用 MiB、UI 算式 `bytes/1e6` 给十进制 MB，并排出现像两个体积）；② **部分/整体不标**（会话只报图塔单文件 345，档位报双塔 754，差的 409 就是文本塔）。

**改动**：`config.py` label 去掉硬编码「（719MB）」；`model_registry.py` 新增 `clip_disk_bytes()` 实算双塔 + `bytes_disk` 字段；`ClipTierSection.vue` 档位改显「双塔 XMB（图塔+文本塔·磁盘实算）」；`BenchmarkSection.vue` 会话实测改显「图塔 345MB + 文本塔 409MB = 双塔 754MB」。**345 + 409 = 754 当场对上。**

## 五、诚实边界

1. **P8–P10 省不掉 walk + stat**。要 100% 确定「没变」就必须看文件；能省的只有解码（占本地耗时 90%+），收益依然巨大。
2. **网络盘上 walk 本身可能慢**（1000 文件的 stat 在 SMB 上可能数秒），但相比「1000 张图完整传下来解码」仍是几十倍改善。
3. **P12 与 P13 相互制约**：影调并行在串行布局下是纯收益；一旦做 P13 阶段重叠，影调会与微服务争核，需重测决定是否保留。
4. **P6 是本轮新发现**，不在 v3 清单里，但它是 T3（收尾后台化）的副作用，优先级不低。
5. **不做「相册级凭记录直接跳过」**：任何不看文件就跳过的方案都会漏掉外部改动（拷入保留旧时间戳的文件、改名等）。若将来确实要做，只能作为显式用户选项，默认关闭。
6. **T6（P17）很可能测出「批次无显著影响」**：这是预期结果，不是失败，价值是用数据证伪。
7. **阶段并行（AI 与图像向量互相并行）不在本清单**：需先压测确认微服务是否单实例串行（同时发 2 个 `/classify_batch` 看总耗时是否翻倍），且当前 `inter_op=1` 已强烈暗示会核心超订，**大概率不可行**。
