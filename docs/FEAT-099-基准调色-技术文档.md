# FEAT-099 基准调色（非破坏图像编辑引擎）技术文档

> 需求来源：「创意工坊下面的图像编辑太不好用了」。原工坊只有一组
> 「算子」（直方图均衡 + 四种模糊），没有摄影调色的基本盘。
> 本文说明新引擎的架构、算法依据、性能取舍与可验证性设计。

---

## 1. 放在 Rust 端还是 Python 端

**结论：整套放 Rust 端，纯 Rust 实现，不依赖 OpenCV / Python 微服务。**

原工坊的算子（均衡化、模糊）走 `python-studio` 微服务（FastAPI + cv2），
由 `src-tauri/src/studio.rs` 拉起。基准调色**刻意不沿用**，理由：

| 维度 | Rust（本模块） | Python 微服务 |
|---|---|---|
| 拖滑块的往返 | 进程内调用，1600px 预览约 10–40 ms | HTTP + multipart 上传 + cv2 转换，100–300 ms |
| 冷启动 | 0（常驻） | python + fastapi + cv2，1–2 s |
| 新增依赖体积 | 0 | cv2 约 60 MB |
| 进程生命周期 | 无需管理 | 需处理 venv 启动器 / 孤儿进程 / 端口回收 |
| 结果确定性 | 逐像素 `f32`，可单测到「逐位相同」 | numpy 隐式 dtype 提升，易出 NaN |

基准调色的核心是「几十次逐像素浮点运算 + 查表」，Python 在这里没有性能优势；
而它对**交互延迟**（每帧都要重算）恰好最不擅长。
微服务保留给「算子形态」滤镜（参数少、不追求实时预览）。

**新增依赖：无。** 只用仓库已有的 `image`、`jpeg-decoder`、`rayon`、`serde`。

## 2. 模块地图（原子化拆分）

```
src-tauri/src/edit/
  mod.rs        模块根 + JPEG/PNG 编码出口            ~130 行
  recipe.rs     配方结构（serde 持久化 / 导入导出）   ~530 行
  schema.rs     参数表（滑块定义，前端据此渲染面板）   ~570 行
  color.rs      色彩空间基础数学                     ~330 行
  tone.rs       线性 HDR 影调                         ~760 行
  curve.rs      色调曲线                             ~470 行
  saturation.rs 饱和度 / 自然饱和度 / 保色相裁剪      ~400 行
  sharpen.rs    带边缘蒙版的 USM 锐化                ~490 行
  geometry.rs   裁剪与拉直（纯坐标数学）              ~470 行
  pipeline.rs   阶段编排 + 工作区（缓冲复用）         ~1050 行
  source.rs     解码与预览分级加载                   ~330 行
  store.rs      sidecar 原子存盘 / 导入导出           ~230 行
  session.rs    编辑会话（跨命令共享源图与工作区）    ~340 行
  commands.rs   Tauri 命令薄壳                       ~700 行
```

**为什么这样切**：

- `recipe.rs` 是**唯一真相源**。它同时是算法输入、持久化格式、导入导出内容
  和撤销栈的快照类型。四个用途共用一个类型，就不会有「存盘的字段」与
  「算法读的字段」不一致。
- `schema.rs` 与 `recipe.rs` 分离：schema 是「**给人看的刻度**」
  （范围/步长/显示格式/帮助文案），recipe 是「给算法看的量」。
  换了刻度只改 schema 一处，不会出现「前端按旧范围钳制、后端已接受新值」。
- `tone.rs` / `curve.rs` / `saturation.rs` / `sharpen.rs` 各自是一个**色彩科学
  单元**，互不依赖。这四个文件里每一个都是可以独立复用的算子，
  也都各有独立单测。
- `geometry.rs` 只做坐标换算，不碰像素。裁剪最容易错的正是坐标系，
  单独成文件让「换错坐标系」这类 bug 一眼可见。
- `pipeline.rs` 只做编排与搬运，**不含任何色彩数学**。
- `commands.rs` 只做参数搬运与错误翻译。

## 3. 处理管线与顺序（顺序即正确性）

```
 0. 几何：裁剪 + 拉直 + 缩放        ← 先定「画哪一块」
 1. sRGB 解码 → 线性                ← 转换点唯一
 2. 白平衡                          ← 必须先于曝光（DNG 规范）
 3. 曝光 + 黑色（**同一公式**）      ← 见 §4.1
 4. 对比度（18% 中灰支点）
 5. 影调分带（高光/阴影/白/黑）      ← 必须在对比度之后
 6. 保色相裁剪 + 线性 → sRGB 编码
 7. 饱和度 / 自然饱和度
 8. 曲线（RGB 后亮度）              ← Adobe: 曲线叠加在影调控件之上
 9. 锐化（显示参考亮度 USM）        ← 在曲线之后、缩放之前
10. 保色相裁剪 + 量化到 u8
```

依据：

- 白平衡先于曝光：DNG 规范明确「white balance is applied first」。
- 曝光与黑色共享一个公式：darktable `src/iop/basicadj.c:1358`。
- 曲线在影调之后：Adobe *Understanding Adobe Camera Raw 3* —
  *"the Curve tab adjustments apply on top of those made by the tonal
  controls in the Adjust tab"*。
- 锐化在重采样之前：Adobe 社区官方答复 *"Sharpening … is all done
  before any resampling on export"*。

## 4. 算法依据与逐项说明

### 4.1 曝光 + 黑色（**一个公式，不是两个**）

```text
out = (x + lift) / (2^-ev + lift)
```

`black = 0` 时恰好退化为 `x · 2^ev`；`ev = 0, x = 0` 时纯黑被抬到
`lift/(1+lift)`。把两者拆成「先减黑 + 后乘 2^ev」两步会得到不同成像，
这是自研调色最常见的错误之一。

`lift` 由黑色滑块映射到 `0..=0.06` 的线性量（sRGB 编码 ≈ 68/255，
再高整片发灰）。

### 4.2 对比度：18% 中灰的幂函数，**按亮度比例缩放**

darktable `data/kernels/basicadj.cl:41`：

```c
float get_contrast(const float x, const float contrast,
                   const float middle_grey, const float inv_middle_grey)
{ return dtcl_pow(x * inv_middle_grey, contrast) * middle_grey; }
```

指数 `= slider + 1`。**绝不能逐通道做幂函数** —— 那会让饱和色的色相随
对比度漂移（红压得多、蓝提得多 → 变橙）。正确做法是算出「亮度该缩放多少」，
再用同一个倍率乘三个通道。

单测守的不变量：**18% 中灰本身不能动**（动了等于同时改了曝光）。

### 4.3 高光 / 阴影 / 白色 / 黑色：EV 域上的 4 个高斯带

这是本引擎最需要解释的一段。

**为什么不能用 gamma**。直觉上「压高光」= 给高光套曲线，但对 gamma
编码值套曲线，同一个 +10 会让暗部跳变而高部纹丝不动 —— 因为 gamma 空间
里 0.9..1.0 只占实际亮度的很小一段。Lightroom 的做法是在
**log2(亮度)（EV）** 域上操作：1 EV 是物理等比间隔，在哪儿都是同样的视觉跨度。

**做法**。四个滑块当作 EV 轴上的四个高斯核：

```text
EV  -9      -5.5   -3.5        -2.4      -1.2   -0.35    0
    |  黑色  | 阴影  |  中间调(对比度支点)  | 高光  | 白色  |

gain(ev) = 1 + Σ_k w_k(ev) · (2^offset_k − 1)
w_k(ev)  = exp(−(ev − c_k)² / 2σ_k²)
```

依据：darktable PR #1904 明确称其 `toneequal` 模块
*"very similar to Lightroom, with blacks/shadows/midtones/highlights/whites
cursors… blended with gaussian masks"*。

**为什么选高斯而不是 smoothstep 分段**：smoothstep 在分段边界处二阶导跳变，
大面积平坦天空上能看到**色带**；高斯 C^∞，累加后依旧光滑。

**为什么白色/黑色用更窄的 σ（0.55 vs 0.9）**：这两个滑块在用户心智里是
「移动最亮/最暗的那一点」，不是「调整一段范围」。窄 σ 保证拖白不会顺带
拉动中间调 —— 单测对此有硬断言。

**一个非常容易犯的错**：写成 `Σ w_k · 2^offset_k`，那么四个「未启用的带」
各贡献 1.0，累加成 **4.0**。必须写成增量形式 `1 + Σ w_k·(2^offset_k − 1)`。
（这个 bug 确实在本项目开发过程中出现过，由 `band_adjustments_never_exceed_neutral_max_in_bright_end`
抓到。）

### 4.4 色温 / 色调：通道乘子

Camera Raw 的白平衡**不是** von Kries/Bradford 色适应，而是**相机空间的三通道
乘子**（darktable `src/iop/temperature.c:431`：`mul[k] = 1.0 / CAM[k]`）。
用 CAT 会得到「更符合色科学但不像 ACR」的结果。

色温用 Tanner Helland 拟合，增益以 6500K 归一化，保证「0 偏移 = 完全中性」。
**额外做一次均值归一化**，使调色温不改变整体亮度 —— 否则用户每调一次
色温都要再拉一次曝光。色调只作用于绿通道，R/B 各补一半维持亮度。

### 4.5 曲线：Catmull-Rom → 256 项 LUT → **保色相**应用

- 插值用 Catmull-Rom：节点处一阶导连续，拖动时「跟手」；
  不用单调三次（Fritsch-Carlson），因为单调约束会削掉所有过冲，
  而「提亮同时保住高光」这类 S 形恰恰需要轻微过冲。
- LUT 256 项（与 Camera Raw 的 `ToneCurvePV2012` 字节数对齐）。
- **RGB 曲线绝不逐通道查表**：把三通道排序，只对 min/max 查 LUT，
  中间通道按「变换后区间内保持相对位置」插值。
  这是 RawTherapee `curves.h:2004` 的 `AdobeToneCurve::RGBTone`
  （注释明写 *"according to Adobe's reference implementation"*）。
  逐通道查表是 PS CS 时代的做法，会让饱和色的色相随曲线漂移。
- 亮度曲线：算 Rec.709 亮度，按倍率缩放三通道，严格保色相。

**前端也必须用同一套插值**（`CurveEditor.vue` 里的 `catmullRom`），
否则用户拖动时看到的曲线与实际渲染不一致。

### 4.6 饱和度 vs 自然饱和度

采用 darktable `basicadj.cl:154-161`：

```c
average = (r+g+b)/3;
P = vibrance * (1 - pow(delta, |vibrance|));   // delta = ‖rgb - average‖
pixel = average + (saturation + P) * (pixel - average);
```

`pixel - average` 是**标量倍数**，所以色相严格不变。
标定：`saturation = slider + 1`、`vibrance = slider / 1.4`。

**指数必须取 `|vibrance|`**。若写成 `1 - delta.powf(vibrance)`（无绝对值），
则在 `delta = 0` 且 `vibrance > 0` 时得到 `1 - 0 = 1`，倍率变成 0 ——
恰好相反，「自然饱和度 +100」会把弱彩度像素洗成纯灰。

### 4.7 锐化：亮度上的带蒙版 USM

四个参数与 Camera Raw 一一对应：**数量 / 半径 / 细节 / 蒙版**，少了任何一个
都无法复现 ACR 的观感。

- 只在 Rec.709 亮度上算残差，把亮度增量等量加回三通道
  → 逐通道 USM 会放大色差，边缘出现彩色描边；
- `σ` 按**短边比例**归一化（`σ_px = (0.5..3.0) × min(w,h)/1000`），
  同一份配方在不同尺寸的图上观感一致；并有 0.6px 的绝对下限
  （否则缩略图上 USM 退化成「减本像素」，把噪点放大成椒盐噪声）；
- `detail` = 残差的软阈值保留比例 → 压光晕；
- `masking` = 残差幅度的 smoothstep 边缘蒙版 → 只锐化强边缘，避开平坦区噪点。

### 4.8 裁剪 / 拉直

- 归一化到「**旋转后画面**」的 0..1（先旋转再裁），
  预览框位置与最终导出一致，换一张图打开时配方仍对得上位置；
- **反向映射**（destination → source）：正向映射在放大时有一半目标像素
  没人写（黑点），反向天然覆盖每个目标像素，缩小时天然多对一重采样；
- 旋转绕**原图中心**进行，画布尺寸按外接矩形调整（否则四角被切）；
- 旋转采样在**sRGB 编码域**（用户眼睛看到的量）做，不在线性域 ——
  线性域动态范围大，插值会让边缘看起来更锐，与「裁剪预览 / 导出结果」
  的锐度对不上。

### 4.9 裁剪（Gamut Clip）

ACES / OCIO 的 `maxRGB` 裁剪：若三通道最大值超上限，用**同一个倍率**压回，
色相与三通道比例严格不变。对比「逐通道 clamp」：红 `(2.0, 0.5, 0.5)`
逐通道得 `(1.0, 0.5, 0.5)`（变暗红），maxRGB 得 `(1.0, 0.25, 0.25)`。

## 5. 性能

| 环节 | 手段 | 量级 |
|---|---|---|
| 预览解码 | JPEG DCT 降采样（`jpeg-decoder::scale`）+ 面积平均二次缩放 | 6000×4000 → 1600px 约 280 ms（首次），之后常驻 |
| 重渲 | 会话缓存解码后的预览平面 | 每帧只剩像素运算 |
| 影调阶段 | 五个阶段**融合成一趟遍历** | 20 MB 平面只读写一次 |
| 影调查表 | 1024 项 LUT（编译一次约 0.3 ms，渲染 N 次） | 9 次 `exp()` → 1 次查表 |
| 拖动档位 | 草稿档长边 800（像素数 1/4）→ 松手后 140 ms 静默期出高清图 | ~1/3 耗时 |
| 缓冲 | `Workspace` 复用，拖动期间零分配 | 避免每次 20 MB 的分配压力 |
| 内存护栏 | 长边上限 12000；会话表上限 8 张 + 30 分钟空闲回收 | 防 OOM |

**预览解码的两级策略**（`source.rs`）不可省：
`Decoder::scale` 只支持 1/1、1/2、1/4、1/8 四档，且判定是「任一轴满足即降档」
（`choose_idct_size` 里是 `||`，实测请求 1600px 会拿到 3000×2000）；
大比例下 DCT 缩放会丢高频（实测与全解码路径 RMSE 达 7.76/255，肉眼可见）。
所以：先向 jpeg-decoder 请求 `目标 × 1.3`（略过冲让档位落得稳），
再用面积平均缩到目标。

## 6. 非破坏编辑 / 持久化 / 导入导出

- **原图永不改动**。全部状态在 `AdjustmentRecipe` 一个结构体里。
- **sidecar 存盘**：`D:\Pics\a.jpg` → `D:\Pics\a.jpg.pmrecipe.json`。
  选 sidecar 而非入库的理由：可移植（拷目录带走）、不侵入 `photos.db`
  的迁移链、冲突天然可见。代价（同一张图被多相册引用时共享配方）正是想要的语义。
  用「原名 + 扩展名」而非替换扩展名，`a.jpg` 与 `a.png` 的配方才能共存。
- **原子写**：写临时文件 → `fsync` → `rename`。
  `rename` 同文件系统内原子；少了 `fsync` 会出现「rename 早于数据落盘」。
  sidecar 是用户资产，写坏了这张图就打不开了。
- **损坏的 sidecar 报错而不是静默当成「没调过」** —— 静默吞掉会让用户
  以为自己调的东西丢了，这是最糟的体验。
- **配方兼容性**：`#[serde(default)]` + 绝不用 `deny_unknown_fields`
  + 绝不删字段（废弃字段保留为 `Option<f32>`）。新增参数不升版本。
- **导入/导出**：JSON 文本（剪贴板或文件）。

## 7. 前端布局（Lightroom 三栏）

```
┌──────────────────────────────────────────────────────────────┐
│ 工具条：打开 保存方案 导入 导出 撤销 重做 自动 对比 导出照片   │
├──────────┬─────────────────────────────┬─────────────────────┤
│ 直方图   │        预览画布 + 裁剪层     │  调整面板（schema） │
│ + 使用提示│                             │  基本/曲线/颜色/    │
│          │                             │  细节/裁剪          │
├──────────┴─────────────────────────────┴─────────────────────┤
│ 状态栏：尺寸 · 档位 · 渲染耗时 · 配方状态                     │
└──────────────────────────────────────────────────────────────┘
```

「左直方图 + 中画布 + 右面板」是 Lightroom 的标志性布局：直方图必须与
画布**同时可见**，否则用户无法边看分布边调曝光 —— 这是调色里最高频的反馈闭环。

### 渲染调度（`stores/edit.ts`）

拖动滑块时若各处直接 `invoke`，会有两个经典问题：

- **请求堆积**：每 16 ms 触发一次而一帧要 30–80 ms，10 个请求排队 800 ms，
  表现为「松手后画面还在慢慢变」；
- **旧结果覆盖新结果**：请求乱序返回时第 5 帧可能后于第 9 帧返回。

解法：同一时刻只允许一个 `invoke` 在飞，飞行期间的调度**合并**成一次
「飞行结束后立刻补一帧」；结果回来后用前端 `renderToken` 校验，
过期即丢弃。后端另有一层序号校验（`session.rs`），两层配合才能同时挡住
排队与乱序。

### 撤销栈

一次拖动 = **一步**撤销（`begin` / `update` / `commit` 三段式），
而不是 50 步。栈深 60。

## 8. 可验证性

### 8.1 独立验证壳 `src-tauri/tools/edit-verify`

`src-tauri` 依赖 Tauri，而 Tauri 在 Linux 上需要 `webkit2gtk-4.1` 等系统
开发包。没有这些包就无法 `cargo test -p photo-management-sys`，
但算法层是纯 Rust。

因此建了 `edit-verify`：通过 `#[path]` 直接引用 `src/edit/**` 的
**同一批文件**（不是拷贝），在没有任何 Tauri 依赖的情况下跑同样的测试。
另配一个同名 `tauri` 桩 crate（`tauri-stub/`）+ 恒等属性宏（`stub-macros/`），
让 **`commands.rs` 也被完整类型检查**。

> 桩的签名必须**与真 Tauri 严格一致**。开发中桩的第一版把 `spawn_blocking`
> 写成返回 `R` 而非 `Result<R, JoinError>`，结果调用点少写一个 `?`
> 也能通过 —— 桩与真 API 一旦不同，整个编译检查就失去意义。
> 它抓到的真实 bug：闭包捕获后仍被使用（move 错误）、
> `PngEncoder::write_image` 在 image 0.25 中不存在、`PathBuf` move 两次。

运行：

```bash
cd src-tauri/tools/edit-verify && cargo test
```

### 8.3 开发过程中被测试抓到的真实 bug（节选）

| 症状 | 根因 |
|---|---|
| 高光被压时整幅图亮 4 倍 | 影调 LUT 写成 `Σ w·2^offset`，未启用的带各贡献 1.0 |
| 色温滑块方向反了 | `wb_gains` 里 tint 只作用于 R/B，没作用在绿通道 |
| 灰调照片「自然饱和度 +100」完全无响应 | 公式写成 `1 - delta.powf(v)`，应取 `|v|` |
| RGB 曲线在 `[0.5, 0.9, 0.1]` 上把排序搞乱 | `order3` 六路 if 链有一个分支写反 |
| 裁剪预览整体偏移半个裁剪框 | `sample_coord` 的归一化坐标漏了 `+0.5` |
| 旋转后画面偏移 `(canvas − image)/2` | 逆映射把「画布中心」当成了旋转轴（应是原图中心） |
| 半幅裁剪被当成恒等变换直接跳过 | `is_identity` 只比数值，没看 `cropped` 标志 |
| 界面永远不出图 | `next_render_seq` 返回 `fetch_add` 的旧值，比对恒为 false |
| 「蒙版开启后噪点没变小」 | 测试在同一个缓冲上连续锐化两次，量到的是累计量 |
| 前端 `writeParam` 会造出拼错的键 | 没检查 `field in bag`，JSON 里多出一个假参数 |

## 9. 自动优化（Auto）

从直方图给一组**保守**的起始值。算法只做单次线性拟合的曝光修正
（不超过 ±1.5EV），只在检测到截断时才动高光/白色，**完全不动**
阴影、黑色、对比度、饱和度、锐化 —— 这几项猜错的代价（噪点、灰雾、假色）
远大于收益。新用户面对 12 个滑块的第一反应是不知道拖哪个，
先给一个「不会把照片弄坏」的起点，体验差别巨大。

## 10. 已知边界

- **不含 90° 整转**。`CropSpec` 只表达 ±45° 的拉直。前端因此**不提供**
  90° 按钮 —— 提供半吊子功能比不提供更糟。要支持需在后端加 `quarter` 字段。
- **不含局部调整（画笔/径向滤镜）**。需要遮罩体系与额外一套混合逻辑，
  是独立的一期。
- **锐化在输出尺寸上做**，与 ACR「全分辨率锐化」相反。理由见 `pipeline.rs`
  头部注释：6000×4000 的 USM 约 1.5 s，缩到输出尺寸后 15 ms；且由于 σ 按
  短边归一化，观感基本一致。需要无损全尺寸时导出选「原始尺寸」即可。
- **JPEG 无 EXIF 方向校正**。手机竖拍的照片不会自动旋转，
  与仓库现有缩略图链路行为一致。
- 会话表上限 8 张 + 30 分钟空闲回收；每张 24MP 图约 45MB（预览 + 工作区）。
