# PhotoManagementSys — 本地相册管理系统

> 本地优先（Local-First）的桌面相册管理应用。内置 AI 视觉识别微服务，实现照片的自动分类、人物识别、场景识别与文字识别。全部数据与推理过程均在本机完成，全程可离线运行。

## 一、项目定位

PhotoManagementSys 是一款面向个人照片库的桌面应用，其核心定位如下：

- **本地存储**：照片与全部管理数据存放于本机，不向任何服务器上传。
- **离线 AI**：内置视觉内容识别（VCR）微服务，基于 ONNX Runtime 在本机完成分类、检测、人脸识别与 OCR 推理。
- **文件夹抽象**：相册是对本地文件夹的抽象。既可将已有图片文件夹直接导入为相册，也可新建相册后再绑定文件夹；相册改名、移动、归类均不影响原始文件。
- **检索优先**：提供时间线、智能搜索、条件过滤、人物总览与回忆视图，支持在数秒内定位数月前的目标照片。

与云相册（需上传、依赖网络、按量付费）不同，该系统以本地存储与离线推理为基本前提，照片与隐私数据不出本机。

## 三、系统架构

系统由三层独立进程与一个独立微服务组成，各层职责明确、按契约协作：

```
┌─────────────────────────────────────────────────────────────┐
│  Frontend  Vue 3 + TypeScript + Vite + Pinia + Vue Router     │
│  （渲染进程，WebView；负责界面渲染、状态管理与后端命令调用）      │
└───────────────┬─────────────────────────────────────────────┘
                │  Tauri IPC（invoke 命令 / 事件）
                ▼
┌─────────────────────────────────────────────────────────────┐
│  Backend  Rust（Tauri 主进程）                                 │
│  命令层 #[tauri::command]  · 业务层 db/photo_scan/thumbnail/    │
│  tone/content/persons/auth/geo_index · 持久层 SQLite            │
└───────────────┬─────────────────────────────────────────────┘
                │  HTTP（REST：HTTP 客户端 ← → 127.0.0.1:8765）
                ▼
┌─────────────────────────────────────────────────────────────┐
│  Microservice  Python VCR（视觉内容识别，独立进程，打包为 exe）  │
│  FastAPI + ONNX Runtime，分层：接口 / 服务 / 持久化 / 基础设施    │
│  模型：YOLOv8 分类/检测 · SCRFD 人脸 · ArcFace 识别 · PaddleOCR │
└─────────────────────────────────────────────────────────────┘
```

各层职责划分如下：

- **Rust 后端**负责本地 I/O 与安全相关工作：文件遍历、缩略图、EXIF、SQLite、密码学。
- **Python 微服务**负责 AI 推理：机器学习生态集中于 Python/ONNX，以独立进程承载，避免向 Rust 引入重型推理栈。
- **Vue 前端**负责界面交互：以组件化与组合式 API 实现快速迭代。

### 技术栈

| 层 | 技术 |
| --- | --- |
| 桌面壳 | Tauri 2.x（Rust） |
| 前端 | Vue 3 `<script setup>` + TypeScript + Vite 6 + Pinia + Vue Router 4 |
| Rust 后端 | rusqlite(SQLite 内置) / image / jpeg-decoder / kamadak-exif / walkdir / argon2 / aes-gcm / reqwest / tokio |
| Python 微服务 | FastAPI + uvicorn + onnxruntime + Pillow + numpy + opencv-python |
| AI 模型 | YOLOv8s/n-cls（分类）、YOLOv8n-det（COCO 检测）、SCRFD（人脸框）、ArcFace（人像向量）、PaddleOCR（文字） |

## 四、模块设计

### 4.1 解耦原则

系统在架构层面明确了模块边界，各模块可独立演进、替换或剥离：

1. **进程级解耦**：Rust 后端与 Python 微服务通过固定 REST 契约通信（`POST /classify_batch`、`GET /health` 等）。开发模式端口固定为 `127.0.0.1:8765`；打包版自 v0.2.0 起改用冷门段动态端口（18765~18865，实例 PID / 端口落盘以便跨重启收养存活服务），彻底避免与其他程序的端口冲突。两侧可独立开发、测试并单独打包。
2. **客户端保持薄壳**：`vision.rs` 为轻量 HTTP 客户端与生命周期管理器，不依赖 `db` / `thumbnail` / `tone` 模块（图片扩展名列表本地复制，防止隐式耦合）；服务不可用或模型缺失时返回明确错误，不影响其他功能。
3. **命令层薄壳**：`lib.rs` 中的 `#[tauri::command]` 仅做参数透传、日志与状态注入，业务逻辑位于 `db` / `content` / `persons` 等模块；`tauri::State` 承担依赖注入职责。
4. **配置集中管理**：Python 端的路径、阈值、模型清单与 GPU 策略集中于 `python/vcr/config.py`，服务层仅引用配置常量。
5. **能力自动降级**：可选模型（场景 / 花朵 / 美食 / OCR）缺失时对应通道自动降级，主分类通道不受影响。

### 4.2 VCR 微服务

VCR（Visual Content Recognition）为独立 Python 服务，将照片交由多路模型推理并仲裁出最终分类，采用经典分层架构：

```
python/
├─ server.py                  # 接口层：FastAPI 路由 + DTO（薄壳，无业务逻辑）
├─ vcr/
│  ├─ config.py               # 基础设施：路径 / 阈值 / 模型清单（集中配置）
│  ├─ model_registry.py       # 基础设施：模型注册表，惰性加载 + GPU 提供方选择
│  ├─ preprocess.py           # 基础设施：图像预处理（缩放 / 归一化）
│  ├─ mapping.py              # 基础设施：ImageNet → 9 大类映射
│  ├─ taxonomy.py             # 基础设施：taxonomy 折叠（保证输出 ∈ 9 类）
│  ├─ schemas.py              # 接口层：Pydantic DTO
│  ├─ persistence/
│  │  └─ person_store.py      # 持久层：SQLite 人物注册表
│  └─ services/               # 服务层：业务编排
│     ├─ classifier.py        #   分类通道（YOLOv8-cls）
│     ├─ detector.py          #   检测通道（YOLOv8-det，人 / 车 / 物）
│     ├─ face_service.py      #   人脸通道（SCRFD + ArcFace）
│     ├─ scene_service.py     #   场景通道（Places365，可选）
│     ├─ ocr_service.py       #   文档通道（PaddleOCR，可选）
│     ├─ flower/food_service  #   专家通道（懒加载，可选）
│     ├─ tone_service.py      #   影调通道（夜景 / 低调判定）
│     ├─ arbitrator.py        #   仲裁器：多通道结果 → 单一结论
│     └─ pipeline.py          #   流水线编排：单张图多路推理 → 仲裁 → 结果
```

关键设计：

- **一次解码，多路分发**：`pipeline.py` 对单张图片仅解码一次，再将张量分发给各专家通道，避免重复 IO。
- **条件触发专家通道**：花朵 / 美食等专家模型为懒加载，仅在判定命中触发条件时加载。
- **仲裁器**：分类、检测、场景、影调、OCR、专家各通道给出候选，仲裁器按阈值与优先级合成唯一结论，保证输出类别属于 9 大类。
- **自动降级**：模型缺失时对应通道自动降级，`/health` 返回真实就绪状态。
- **GPU 可选**：默认自动检测 onnxruntime GPU 提供方（DirectML / CUDA），有则用 GPU，无则回退 CPU；可通过 `VCR_PROVIDER=cpu` 强制 CPU。

### 4.3 前端组件复用

前端以组件化与组合式 API 实现界面复用：

- **通用基础组件**：`Toast` / `ToastContainer`（全局通知）、`ConfirmDialog`（确认框）、`CollapseSection`（折叠面板）、`PhotoGrid`（照片网格）、`PhotoLightbox`（灯箱）、`AlbumCard` / `AlbumMiniCard`（相册卡片），在首页、相册列表、时间线、回忆等多个视图复用。
- **复杂视图拆分**：`AlbumDetail.vue` 由 2709 行重构至 183 行，拆分为 `AlbumMeta`、`PhotoGrid`、`CollapseSection` 等子组件，各子组件职责单一，父组件仅做数据装配。
- **状态集中管理**：跨视图共享状态（album / content / toast / theme / auth）集中于 Pinia store，组件通过 store 读写，避免逐层 props 传递。
- **组合函数复用**：`useNotify.ts` 将通知触发逻辑封装为组合函数，任意组件可一行调用。
- **类型驱动开发**：`types/` 中定义 `Album` / `Photo` / `Content` 等类型，与后端 serde JSON 一一对应，契约清晰，字段变更可在编译期发现。

## 五、性能优化

开发过程中实施的典型优化如下：

- **缩略图 DCT 降采样解码**：全尺寸解码 6000×4000 巨图需 5~14 秒；改用 `jpeg-decoder` 的 `scale` 仅解码所需 DCT 块后，切换封面耗时由 7.7s 降至 0.76s（约 10 倍）。缩略图缓存写入 `app_data_dir/thumbs`，不写回数据库。
- **批量内容识别**：`/classify_batch` 单次最多处理 64 张（客户端默认 8），配合分批提交与 `classify-progress` 事件实时上报进度。
- **GPU / 批次加速**：识别服务自动探测 GPU（DirectML），可用时走 GPU；否则 CPU 多线程（`THREADS=4`）。
- **GPS→省市离线反查**：内嵌省市边界数据，以点面判断在离线状态下反查照片地理位置，替代逐张联网反编码，兼顾速度与隐私。
- **组合扫描三合一**：EXIF（拍摄时间）、影调（曝光 / 夜景）、AI（内容识别）在一次组合扫描中完成，减少重复遍历。
- **分页加载**：照片网格分页渲染，避免大相册一次性渲染造成卡顿。
- **多用户安全**：密码采用 Argon2id（抗 GPU 暴力破解）；邮箱 / 手机号 / 密码哈希以 AES-256-GCM 加密落库。

- **方式一（推荐）**：下载 Release 中的安装包并双击安装（最新稳定版 **v0.4.5**，约 105MB，内含 VCR 微服务但**不含 AI 模型**——见下方「模型放置说明」与「十一、版本历史」）：
  - [`PhotoManagementSys_0.4.5_x64-setup.exe`](https://github.com/howforever2000/PhotoMangementSys/releases/download/v0.4.5/PhotoManagementSys_0.4.5_x64-setup.exe)（NSIS，按用户安装到 `%LOCALAPPDATA%`，无需管理员权限，推荐）

  - 可选组件（仅 Intel NPU 用户需要）：[`openvino-npu-win-x64.zip`](https://github.com/howforever2000/PhotoMangementSys/releases/latest/download/openvino-npu-win-x64.zip)（15.5MB）—— 不装则全部走 ONNX Runtime，行为与旧版一致；装了可在「性能设置」里让检测 / OCR / 人脸编码走 NPU
  - 从旧版升级：建议先卸载旧版再安装（两种安装范围不同，否则会同时存在两份）
  - 历史版本（v0.4.4 / v0.4.3 / v0.4.2 / v0.4.1 / v0.4.0-beta / v0.3.x / v0.2.0 / v0.1.0）见 [Releases](https://github.com/howforever2000/PhotoMangementSys/releases)
- ⚠ **v0.4.3 起应用标识符改为 `com.photomanagementsys.app`**（原 `com.haoyuan.photo-management-sys` 会把作者姓名带进每台用户机的 `%APPDATA%` 目录名）。数据目录随之变化，首次启动会自动把 `photos.db` / `thumbs` / `vcr-data` / `app.key` 一次性迁移到新目录（优先 rename，失败则复制，**仅在复制成功后删旧目录**；新目录已有数据则不覆盖、只提示旧目录位置）。
- 安装包不含 AI 模型（详见「七、构建与发布」）。请按「模型放置说明」将模型文件放入模型目录后再启动，否则识别与语义搜索不可用（看图 / 相册管理 / 压缩不受影响）。

### 6.2 首次使用

1. **注册账号**：以账户名 / 邮箱 / 手机号 + 密码注册（同机可多用户，相册相互隔离）。
2. **导入照片**：在「相册管理」页新建相册并选择本地图片文件夹，系统将扫描其中的图片（支持 jpg / jpeg / png / webp / gif / bmp，以及 iPhone 默认的 heic / heif —— HEIC 依赖系统「HEIF 图像扩展」解码，缺扩展时应用内会提示，EXIF 与入库不受影响）。
3. **启动 AI 识别**：在详情页执行「内容识别」/「组合扫描」，进度条完成后每张照片自动归类（动物 / 食物 / 建筑 / 夜景 / 人像等），人物自动聚集。

### 6.3 日常使用

- **时间线**：跨相册按时间浏览全部照片。
- **智能搜索**：输入关键词或组合「条件过滤」（EXIF 拍摄时间 / 影调 / AI 类别）精确检索。
- **人物总览**：进入人物页，对人物进行改名、合并（同一人多张面孔）、删除误检。
- **手动整理**：在「分组」中创建文件夹树并将相册批量移入；在「手动排序」中调整顺序；为相册批量设置地点 / 标签。
- **重复照片清理**（扫描入库 → 重复扫描清理）：全库范围内按「内容哈希一致」（字节完全相同）与「图像向量相似度 ≥ 阈值（默认 0.98，0.80–1.00 可调）」两类判据分组，每组默认保留分辨率最高的一张，其余可自主勾选后「仅删除记录」或「移入回收站」。同一个真实文件（相册 A 与其子相册 B 都入库、或同名文件的 junction／短名写法）只算一张，卡片下方显示照片所在地址，点缩略图可直接看大图；结果按屏增量渲染，缩略图进视口才加载。
- **入库体检**（扫描入库 → 入库体检）：检查「扫描入库」写下的数据是否还和磁盘对得上 —— 逐册看**入库覆盖率**（磁盘有、库里没有的漏扫）、**缩略图 / 图像向量覆盖率**、相册根目录是否还在、以及抽样核对「记录指向的文件是否已不存在」，并给出缩略图缓存占用。全程**只读**，不改库、不重扫；每条问题带「去扫描 / 打开相册」入口。
- **批量导出**：选中多张照片一键导出到指定文件夹。
- **回忆**：进入「回忆」视图查看基于人物 / 地点 / 节日的聚合。

### 6.4 隐私与安全

- 照片、缩略图与人物数据全部存放于本机 `app_data_dir`，绝不上传。
- 跨机迁移时，拷贝照片文件夹并重新导入即可；相册元数据随 `photos.db` 整体迁移。

## 七、构建与发布

### 7.1 依赖说明

- **主程序**：Tauri 编译产物 `PhotoManagementSys.exe`（内嵌 Rust 后端与 Vue 前端）。
- **VCR 微服务**：独立打包为 `vcr-server.exe`（PyInstaller 单文件，约 85MB，含 Python 运行时与依赖），随安装包内嵌至安装目录 `vcr/`。
- **AI 模型**：`.onnx` 模型文件体积较大，不入 git 仓库（由脚本下载 / 导出生成），随安装包内嵌至 `vcr/models/`，或由用户按说明放置。

### 7.2 模型放置说明

默认安装包已包含模型。若安装包不含模型，请确认模型目录下存在以下文件（v0.4.5 架构：**图像分类模型已下线**，内容分类改由语义模型驱动；**语义模型只剩 fp32 一档**）：

```
vcr/models/
├─ yolov8n-det.onnx                          # COCO 检测 / 人物（必选）
├─ det_10g.onnx + w600k_r50.onnx             # 人脸高精度档（默认；仅当它是当前档时必选）
├─ det_500m.onnx + w600k_mbf.onnx            # 人脸轻量档（性能设置里可切，可缺）
├─ paddleocr-det.onnx                        # 文档 OCR（可选，缺失自动降级）
├─ chinese-clip-fp32/                        # 语义模型（B/16 fp32 单档，必选）
│  ├─ onnx/model.onnx                        #   双塔整图（首次使用自动拆成 vision/text 子图）
│  ├─ tokenizer.json                         # ⚠ 必须与 onnx/ 同级，不能放进 onnx/ 子目录
│  └─ vocab.txt
└─ _runtime/                                 # 可选组件（Intel NPU 才需要）
   └─ openvino-npu-win-x64.zip               #   解压产物 _runtime/ovrt/ 由服务首次使用时生成

可选组件：`_runtime/openvino-npu-win-x64.zip`（15.5MB 下载 / 45.4MB 装后，仅 Intel NPU）——

已下线（不再需要）：`yolov8*-cls.onnx`、`resnet18_places365.onnx`、`album_groups.json`、`imagenet_*.txt/json`。

### 7.3 模型获取与更新

- **应用内下载（v0.2.0+，推荐）**：「⚙ 性能设置 → 模型管理」可后台下载人物检测 / 人脸两档 / OCR / 语义（B/16 fp32）与 OpenVINO 可选组件，官方 / 镜像源双路竞速 + 断点续传。

- **检测 + 语义子图**：直接复制开发机 `python/models/` 下对应文件；语义双塔整图首次使用时由服务自动拆成 `clip_vision.onnx` / `clip_text.onnx`（幂等 + 与整图数值对齐校验，需模型目录**可写**，见 7.4）。前者失效时，服务会自动回退到旧布局 `chinese-clip/`（仅当里面已有 fp32 整图或拆分件）。

### 7.4 发布打包

在项目根目录执行：

```

脚本依次执行：① 以最小化 venv 构建 `python/dist/vcr-server.exe` → ② 校验 / 补齐模型 → ③ `npm install` → ④ `npx tauri build --config src-tauri/release.tauri.conf.json`（合并 release 配置，将微服务与模型内嵌进安装包）。

两点约定（v0.3.0 起）：

- **内嵌模型走显式清单**：`src-tauri/release.tauri.conf.json` 的 `bundle.resources` 逐项列出运行必需模型（不再整目录内嵌），避免把开发用 / 已下线的模型打进安装包（v0.3.0 安装包因此从 574MB 降到 457MB）。新增必需模型时记得同步该清单与 `release.ps1` 的校验列表。

产物位置：`src-tauri/target/release/bundle/msi/` 与 `nsis/`。

## 十、常见问题

**Q：`/health` 显示 GPU 不可用？**
打包版默认使用 CPU 推理。v0.2.0 起可在「扫描中心 → ⚙ 识别性能设置」中开启 GPU 加速（DirectML / CUDA 优先，切换即重建 ONNX 会话）。若开启后仍不可用，说明内置 onnxruntime 不含对应提供方，需使用 `onnxruntime-directml` / CUDA 版重新打包微服务；开发版可 `pip install onnxruntime-directml` 并设置 `VCR_PROVIDER=auto`。

**Q：扫描慢 / 想调扫描线程数？**
「相册扫描分组工具」操作栏里有独立的「⚙ 性能设置」（与识别性能设置分开：那是 GPU 与推理线程数，这是文件扫描的并行度）。默认值由本机 CPU 拓扑与磁盘类型算出（物理核 + 超线程折扣，机械盘限 4 线程），可直接下拉改；也可点「📊 按当前相册实测最优线程」——程序会取该目录的真实文件分层抽样，在多个档位实测后给出最优值（定义为「达峰值吞吐 95% 的最小线程数」）。扫描/解析地名/组织移动都在**后台执行**，离开页面不会中断。

**Q：更换电脑后，相册中的照片是否可找回？**
照片为本地文件，仅与文件夹路径绑定。将照片文件夹一并拷贝至新机并重新导入即可；标签 / 分类数据建议连同 `photos.db` 一并迁移（需使用同版本）。

**Q：识别服务未启动 / 提示「模型未加载」？**
检查 `vcr/models/` 下是否存在对应 `.onnx` 文件；若无，按「七、构建与发布」获取。开发版需先安装 `python/requirements.txt`。

## 十一、版本历史

### v0.4.5（2026-11-01）— 推理加速接 NPU / 语义模型收敛单档 fp32 / 重复照片清理 / 扫描入库分区与体检 / 灯箱重排（FEAT-134~143、150~153）

本版四个方向：**把 AI 腿的瓶颈真正拿掉**（NPU + 加速分配表，真机实测 -58.4% ~ -70.6%）、
**语义模型收敛为一档 fp32**（删掉双输的 fp16 默认档且老用户零重建）、
**新增重复照片清理**（内容哈希 + 向量相似两套判据、两档删除）、
**扫描入库与灯箱的界面收口**，另将创意工坊从调色台改为图像加工工具台。

**加速：三条腿接 NPU + 加速分配表 + 运行时改可选组件（FEAT-135/136/139/140/141）**

先量清楚再动手：真正的瓶颈不是单模型跑多快，而是 **DirectML 单队列的加锁次数**
（持锁占墙钟 98%、每张 116 次加锁）。因此收益 ≈ 「从 DML 队列里拿走多少次加锁」。
据此把加锁最密的 det（每张 1 次）/ ocr（约 72% 图 1 次）/ face_rec（每脸 1 次）三条通道交给 NPU，
face_det（det_10g 在 NPU 上慢 7×）**永久排除**。

- 实测（53 张探针，摊薄墙钟）：cpu 145.2 → dml 85.7 → 三腿 NPU **43.0** ms/张；
  983 张真扫描 **328.2s → 136.6s = -58.4%**（336.6 → 140.1 ms/张）；
  300 张用分配表形态 **87.7s → 25.8s = -70.6%**；200 张子集 -55.5%，量级一致。
- 数值等价（不拿速度换正确性）：det 人框 **53/53 零差异**；w600k_r50 在 38 张真人脸上 cos 最小 **0.99997220**；
  paddleocr 掩码 IoU 中位 **1.0000**（6/53 张差 1 个文本框）；端到端分类硬字段 53/53 一致、`confidence|Δ|≤0.0007`。
- **加速分配表**：每个通道可单独指定设备（持久化在 `current_accel.json`），界面改成 **NPU / 核显两个独立勾选**
  （硬件或组件不具备的那一项不显示），勾选本身就是意图，不再要用户从「请求 / 实际」两列表里反推开关的作用范围。
  四组合实测（读 ORT 实际绑定）：只勾核显 → 全 GPU；只勾 NPU → {NPU,CPU,NPU,NPU}；都勾 → {NPU,GPU,NPU,NPU}；都不勾 → 全 CPU。
- **加速默认开启**：`current_accel.json` 不存在时按 `mode=auto` 生效（旧版是「不点开关 = 不加速」，
  等于默认最慢那档）；表格最后一行固定写「缩略图 · EXIF · 地点 → 始终 CPU」，明确这个开关不影响什么。
- **语义索引（CLIP）进分配表**：以前 CLIP 跑在 CPU 还是 DML 取决于「用户点没点过加速开关」，两处界面都没写。
  现在可看可切（实测会话表在 CPU ↔ DirectML 间真实翻转）；**默认 CPU** 是量出来的取舍 ——
  日常增量重扫才是常态，首次导入大批照片时可一键改核显（-27%~-45%）。
- **OpenVINO 运行时改为可选组件**：完整版 244.8MB，裁掉编译器(95.7MB)+CPU 插件(44.2MB)+GPU 插件(33.1MB)
  后 **15.5MB zip / 45.4MB 装后**，不进安装包（AMD/NVIDIA 用户完全用不上），由应用内按需下载后交 Python 标准库解压。
  裁剪版已实测 `compile_model(onnx, "NPU")` 可用且输出与完整版一致。**不装 = 行为与旧版逐字一致**。
- **删掉「线程测速」扫档**（6 分钟却调错对象）：它对着只占扫描 0.2% 的 CLIP 图塔扫 7 档，
  写进去的却是 det/face/ocr 共用的全局 `intra_op`。CLIP 线程数与其解耦：默认取用户线程数一半，夹在 `[4, 全局线程]`。
- 两项修复：性能设置显示「语义索引 · NPU 已启用」但 NPU 占用恒为 0（stderr 写失败把一次成功的加载改写成了失败，
  语义腿整段被跳过）；切换语义塔后端后 `/health.clip_ready` 恒为 false（UI 说启用、服务说没就绪）。

**语义模型收敛为单档 fp32（FEAT-137）**

fp16 档下线，只留 B/16 **fp32**：实测 256px 缩略图上 fp16/CPU 74.4~113.7 ms/张、fp32/CPU **60.6~76.4 ms/张**
（x86 上 ORT 跑 fp16 权重必须反复 cast），而 fp16 又**永远拿不到 GPU**（DirectML 上有算子级数值 bug）——
旧默认档是双输。两档精度等价（32 张图 cos 最小 0.99999887）。
**老用户零重建**：fp16 / fp32 两个旧向量标签在宿主启动时被重打成中性 id `chinese-clip-vit-b16`，
万张库约 13 分钟的重编码被完全避开；旧 `chinese-clip/` 目录里若已有 fp32 整图也会被直接复用（不白下 719MB）。

**重复照片清理上线（FEAT-143）**

- **两套判据**：① **内容哈希**完全相同 = 精确重复（注意：不复用既有 `photo_hash`，它含路径，副本必然不同）；
  ② **CLIP 向量相似度**超过阈值 = 相似（滑杆 0.80~1.00，默认 0.98）。两个开关可同时用。
- **两档删除**：「仅删记录」（文件还在，可从最近删除恢复）/「移入回收站」（进系统回收站并级联清缩略图与扫描记录），
  两个独立按钮 + 各自确认文案，避免点错档。全选可用，默认保留每组第一张（原图）。无向量的照片跳过并在结果里如实报数。
- **性能**：体积预筛（体积唯一的图直接跳过，不读盘）+ 方差最大维 + 柯西-施瓦茨窗口剪枝；
  三段并行 + AVX2 内积；相似分组改**完全链接**（不会出现「A 像 B、B 像 C 就把 A 和 C 算一组」的链式错误）。
- **结果呈现**：按文件夹折卡（一个文件夹一张、标 N 份，文件夹整卡锁死）+ 翻页 + 页内视口热加载。
- 三项修复：父子相册里的同一张照片被当成两条并列（勾选后会对同一文件发两次删除指令、可释放体积虚高）；
  扫描完成时界面长时间卡住（一次铺整页卡片 + 上千张缩略图一起入队）；
  同文件夹多份相同照片被平铺成 3 张一样的缩略图、地址还与「保留」那张相同而不敢点删除。

**HEIC/HEIF 支持（FEAT-142）**

iPhone 照片现在能进扫描列表、出缩略图、进向量索引（此前相似去重对 iPhone 图完全失效）。
解码走**系统 WIC**（零新增依赖、零分发体积；pure-rust heic 是 AGPL-3.0，libheif 要 vcpkg 编 C 库），
代价是依赖用户机器装了 HEIF 扩展 —— 所以做了探针与降级提示，而不是假装能用。
EXIF 与像素解耦（容器内 item 直接读）：缺解码器时损失从「照片完全不可用」压到「只影响缩略图/预览/向量」。
按 major brand 排除 `avif/avis`（它们常把 `mif1` 写进兼容列表，误路由会让用户装错扩展）；
HEIC 的旋转是容器属性 `irot/imir`、系统解码器已烘焙，预览链路不再二次套 EXIF Orientation。

**灯箱（大图预览）版式重排（FEAT-134）**

「不好看」的根因是**浮层数量与层级**而不是配色：同一块照片上叠了顶部快捷键胶囊 + 底部工具栏两条 chrome，

交互面（窗口范式 / 快捷键 / emit）零改动，回滚只需还原 template + style。

**扫描入库：分区统一 + 入库体检 + 明细日志（FEAT-151/152/153）**

- **分区统一**：相册扫描分组工具改成路由型 tab 一跳直达（与其他模块一致）；
  分组工具页自带的那份硬编码分区删掉，**同一份分区表喂两个页面** —— 过期状态（比如「重复清理待开发」）无处藏身。
